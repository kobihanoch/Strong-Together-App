## Purpose

Strong Together uses **DPoP** to add proof-of-possession behavior to mobile API calls. Instead of treating a bearer token as the only proof, the client signs requests with a persisted device key pair so the backend can bind tokens to the client that received them.

## Key Pair Lifecycle

At app startup, `ensureDpopKeyPair()` makes sure the client has an **ES256** key pair.

The flow is:

1. Try to load `dpop_private_jwk` and `dpop_public_jwk` from Expo SecureStore.
2. If both exist, parse and cache them in memory.
3. If either key is missing, generate a new ES256 key pair with `jose`.
4. Export both keys as JWKs using `global.crypto.subtle.exportKey`.
5. Persist the JWKs in SecureStore.

The app stores JWK values instead of long-lived `CryptoKey` objects so the keys can be restored reliably across app launches and JavaScript runtime boundaries.

## Token Binding

For guest auth requests, the request interceptor adds a `dpop-key-binding` header.

That value is the **JWK thumbprint** of the public key:

1. Build a canonical public JWK from `crv`, `kty`, `x`, and `y`.
2. Hash it with SHA-256.
3. Encode the hash as base64url.

The backend can use this thumbprint when issuing tokens so later requests must be proven with the same key pair.

## Request Proofs

Authenticated requests receive a `dpop` header generated by `buildDpopProof()`.

Each proof is a signed JWT with:

- `jti` - unique id for the proof
- `htm` - HTTP method
- `htu` - absolute request URL without query noise
- `iat` - issued-at timestamp
- `ath` - access token hash when an access token is available

The protected header includes:

- `alg: ES256`
- `typ: dpop+jwt`
- the public JWK

The proof is signed with the persisted private JWK, which lets the backend verify that the request came from the holder of the matching private key.

## Access Token Hash

`calculateATH()` creates the `ath` claim by hashing the access token with SHA-256 and base64url encoding the result.

This binds the proof to the current access token. If someone copies only the token without the private key, they still cannot produce a valid request proof.

## Why This Matters

This flow adds a meaningful security layer for a mobile app:

- refresh tokens stay in secure storage
- access tokens live in memory
- login can bind issued tokens to a device key
- authenticated requests include signed proof material
- replay and token-copy risk is reduced compared with plain bearer-token calls

It is a small part of the UI surface, but it reflects a production-level approach to authentication and API trust.
